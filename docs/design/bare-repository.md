# ベアリポジトリの設計判断

本ドキュメントは、並列エージェントアーキテクチャにおいてローカルのベアリポジトリを採用する理由を、GitHub との比較を交えて解説したものである。

---

## ベアリポジトリとは

普通の git リポジトリとの違い:

```
通常のリポジトリ (git clone で作るやつ)
├── .git/          ← Git のメタデータ
├── src/           ← 作業ファイル (working tree)
├── Cargo.toml
└── README.md

ベアリポジトリ (git init --bare で作るやつ)
├── objects/       ← .git/ の中身がそのまま
├── refs/          ← トップレベルに展開されている
├── HEAD
└── (作業ファイルなし)
```

**`.git/` の中身だけのリポジトリ**。作業ファイル（ソースコード等）が一切ない。GitHub のサーバー側も内部的にはこれ。

---

## アーキテクチャ

```
                    ┌─────────────────┐
                    │  Bare Repository │ ← 作業ファイルなし
                    │   /upstream/     │    push先・pull元として
                    │                  │    機能するだけ
                    └──┬────┬────┬──┘
                       │    │    │
            git clone  │    │    │  git clone
                 ┌─────┘    │    └─────┐
                 ▼          ▼          ▼
            ┌────────┐ ┌────────┐ ┌────────┐
            │Agent 1 │ │Agent 2 │ │Agent 3 │
            │        │ │        │ │        │
            │/work/  │ │/work/  │ │/work/  │  ← 各自の作業コピー
            │ src/   │ │ src/   │ │ src/   │
            │ ...    │ │ ...    │ │ ...    │
            └────────┘ └────────┘ └────────┘
```

各エージェントは:
1. ベアリポから `git clone` して自分専用の作業コピーを作る
2. そこでコードを編集・コミット
3. ベアリポに `git push`
4. 他のエージェントの変更は `git pull` で取得

---

## 通常のリポを直接共有したらダメな理由

作業ファイルのあるリポを 16 エージェントが共有すると:

```
Agent 1: vim src/parser.rs   ← ファイルを編集中
Agent 2: vim src/parser.rs   ← 同じファイルを同時に編集!
Agent 3: cargo build         ← Agent 1 の編集途中でビルド!?
```

ファイルシステムレベルで衝突して壊れる。

ベアリポなら各自が独立した作業コピーを持ち、Git プロトコルが排他制御を担保する。

---

## GitHub ではなくローカルベアリポを使う最大の理由: 速度

このアーキテクチャの根幹は push が失敗したら pull → retry のループ:

```
Agent A: git push  ──→  ❌ rejected
         git pull  ──→  マージ
         git push  ──→  ❌ rejected
         git pull  ──→  マージ
         git push  ──→  ✅ success
```

16 エージェントが同時に動くとこの retry が頻発する:

```
ローカルベアリポ:
  git push  → ~10ms   (ファイルシステム内コピー)
  git pull  → ~10ms
  retry 1回 → ~20ms

GitHub:
  git push  → ~1-3秒  (ネットワーク往復)
  git pull  → ~1-3秒
  retry 1回 → ~3-6秒
```

実際のデータで 03:52 に 3 エージェントが 45 秒以内に push していた。GitHub 経由だとこの競合解決ループが**100 倍以上遅い**。

---

## 比較表

| | ローカルベアリポ | GitHub |
|---|---|---|
| push/pull 速度 | ~10ms | ~1-3 秒 |
| レートリミット | なし | あり（1 時間あたりの制限） |
| 認証設定 | 不要 | 各コンテナにトークン必要 |
| 外部依存 | なし | GitHub 障害で全停止 |
| コスト | ゼロ | 無料枠内なら無料 |
| 監視 UI | なし | Web UI で見られる |

## ハイブリッド運用

```bash
# 作業中はローカルベアリポ（高速同期）
# 定期的に GitHub にミラーpush（人間が監視用）
while true; do
    sleep 300  # 5分ごと
    cd /upstream
    git push github-mirror main
done
```

実際、最終的にこのリポジトリは `anthropics/claudes-c-compiler` として GitHub に公開されたが、それは開発完了後に push したもの。開発中の 16 エージェントの高頻度 push/pull は、ローカルで完結させた方が合理的。

**ベアリポは「GitHub の代わりにローカルに置いた中央リポジトリ」。ネットワーク遅延ゼロの自前 GitHub。**
