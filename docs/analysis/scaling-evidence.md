# 段階的スケーリングは手動か自動か

本ドキュメントは、claudes-c-compiler リポジトリのコミットパターンから、エージェントの段階的スケーリングが手動で行われたか自動で行われたかを検証した結果をまとめたものである。

**結論: ほぼ確実に人間が手動でコンテナを追加した。**

---

## 証拠 1: 直列期間が長すぎる

もし 16 コンテナが同時起動していたなら、scaffold（01:30 完了）直後に 15 エージェントが一斉に Lock を取りに行くはず。しかし実際には:

```
01:30  scaffold完了 → 5,657行のコードが利用可能に
01:37  Lock: array subscript         ← 1エージェント目のみ
01:54  Implement array subscript
02:09  Lock: type-aware codegen      ← まだ1エージェントだけ
 ...（85分間、完全に直列）...
02:55  Lock: typedef tracking        ← ★ やっと2エージェント目が出現
02:57  Lock: switch lowering
```

**85 分間もの間、コードベースが十分にある状態で 1 エージェントしか動いていない。** 16 エージェントが待機していたなら、ここで一斉にタスクを取りに来るのが自然。

---

## 証拠 2: 並列度の段階的な増加パターン

| 時刻 | 並列度 | イベント |
|---|:---:|---|
| 01:04〜02:49 | **1** | scaffold 構築 |
| 02:55 | **2** | 2 つ目の Lock が同時に存在 |
| 03:34 | **3〜4** | 初のタイムスタンプ逆転(commit #23) |
| 03:47 | **6+** | `Starting new run; clearing task locks` → 爆発的増加 |
| 05:38 | **8+** | 2 回目の `Starting new run` → さらに増加 |
| 06:00〜07:00 | **13〜17** | ほぼフル稼働 |

増加のタイミングは不規則で、メトリクスベースではない。

---

## 証拠 3: `Starting new run` の前に 1 時間の空白がある

```
04:32  最後の活発なコミット
  ~~~ 65分間の完全な沈黙 ~~~
05:38  Starting new run; clearing task locks
05:40  Lock: fix backend consistency
05:40  Lock: refactor backend dedup  ← 25秒差で2つ同時
```

この 65 分の空白は、人間がログを確認し、設定を調整し、コンテナを再起動/追加した時間と解釈するのが自然。

---

## 証拠 4: ブログの記述との整合性

ブログ記事は「16 agents に任せて mostly walked away」と書いているが、README には:

> *A human guided some of this process by writing test cases that Claude was told to pass*

とあり、人間の介入があったことは認めている。さらに `ideas/IMPORTANT_implement_ssa.txt` のコミットメッセージ:

```
"Tell it to implement SSA"
```

これは明らかに人間が ideas/ ディレクトリにファイルを直接配置して、エージェント群への指示を出した痕跡。

---

## 推定されるオペレーション手順

```
[人間] 1コンテナ起動、scaffold生成を確認
         ↓ (約2時間後)
[人間] 2-3コンテナ追加、並列動作を確認
         ↓ (約30分後)
[人間] さらに追加 → 03:47 の再起動イベント
         ↓ (1時間の確認・調整期間)
[人間] 05:38 に8+コンテナで再起動
         ↓ (段階的に追加)
[人間] 06:00-07:00頃に16コンテナでフル稼働
```

ブログ記事が「16 agents を投入して walked away」と表現しているのは、フル稼働に達した後の話であり、0→1 のブートストラップフェーズでは人間がかなり慎重に段階的スケーリングを行ったと考えられる。
